# BRA v1.5（C 组）设计与契约：字典 / 定时任务 / 通知公告 / i18n / 体积

日期：2026-10-06 · 基线 v1.3.0（阶段 1 的 A+B 组另见同日的 A+B 批次）· 本文是 **C 组四项**的设计与接口契约，
实现按本文执行。每项落地后单独发版（v1.5.0 字典 → v1.6.0 任务与公告 → v1.7.0 i18n → v1.8.0 体积），
避免一个大版本里混着四种性质不同的改动。

## C1 字典管理（v1.5.0）

**用途**：把「不改代码就能改的配置项」（性别、状态、业务枚举）搬进后台，前端下拉从这里取。

**数据模型（2 张表，走 syncdb）**

```
dict_type(id pk auto, name varchar64, code varchar64 UK, status i8, remark varchar255, created_at, updated_at)
dict_item(id pk auto, type_code varchar64 idx, label varchar64, value varchar64,
          sort i32, status i8, remark varchar255, created_at, updated_at,
          UNIQUE KEY uk_type_value(type_code, value))
```
- 字典项按 `type_code` 关联（不建外键，与现有风格一致）；`uk_type_value` 防同类型下 value 重复。
- 删除字典类型时**级联删除其字典项**（同一事务）；删除前若被引用？——本项目没有引用字典的地方，不校验。

**接口**（权限码 `system:dict:list/add/edit/remove`；菜单挂在系统管理下）

```
GET    /api/v1/dicts?page&size&name&status        → Page<DictType>
POST   /api/v1/dicts                              { name, code, status, remark }
PUT    /api/v1/dicts/{id}                         { name, status, remark }（code 不可改：它是关联键）
DELETE /api/v1/dicts/{id}                         级联删项
GET    /api/v1/dicts/{code}/items                 该类型全部启用项（**前端下拉用，登录即可访问**，不要求 system:dict:list）
GET    /api/v1/dict-items?page&size&type_code&label&status  → Page<DictItem>
POST   /api/v1/dict-items                         { type_code, label, value, sort, status, remark }
PUT    /api/v1/dict-items/{id} / DELETE /api/v1/dict-items/{id}
```
- `GET /dicts/{code}/items` 是**唯一对普通登录用户开放**的字典接口（下拉数据源）；其余都要权限码。
  返回 `[{label, value}]`，只含 `status=1`，按 `sort, id` 排序。
  **两种语义必须分开**（前端联调时发现原来混在一起）：类型不存在 → **404**（「字典类型不存在」，
  否则拼错 code 的人看到的是"空下拉"，分不清"没配数据"和"code 写错"）；类型存在但没有启用条目
  → **200 + `[]`**（合法状态，不是错误）。
- 导出：字典项列表也支持 `GET /dict-items/export`（复用现有 CSV 机制）。

**两个已知的刻意差异**（记录以免以后被当成 bug）：
- **列表排序与下拉同序**（`sort ASC, id ASC`），而**导出仍按 `id DESC`**（流式导出用 keyset 分批，需要稳定的 id 序）
- **删除字典类型会级联删项**（同一事务），创建条目则校验 `type_code` 必须存在（400），避免孤儿项

**前端**：`system/dict/` 一页两栏（左类型列表、右该类型的字典项表格 + 增删改），路由 `/system/dict`，
守卫 `system:dict:list`；另加一个 `useDict(code)` hook（带内存缓存）供其他页面的下拉使用。
**缓存失效**：任何修改字典项的页面，成功回调里必须 `dictCache.delete(code)`——漏了的表现是
别处下拉显示旧选项（前端已在字典页三处调用点落实）。

**验收**：字典类型/项的增删改查真库集成测试；级联删除；`{code}/items` 只返回启用项且普通用户可访问。

## C2 定时任务 + 通知公告（v1.6.0）

### C2a 定时任务

**目标**：后台里能看到「有哪些定时任务、上次跑成什么样、能不能手动跑一次」。**不做**在界面上写任意脚本
（那是 RCE 面）——任务用**代码注册**，数据库只管调度与执行记录。

**数据模型（2 张表）**

```
job(id pk auto, name varchar64, code varchar64 UK, cron varchar64, status i8,
    last_run_at DATETIME NULL, last_status i8 NULL, last_msg varchar255, created_at, updated_at)
job_log(id pk auto, job_code varchar64 idx, started_at DATETIME, duration_ms u64,
        status i8, msg varchar255, KEY idx_code_time(job_code, started_at))
```
**调度器**：不做 cron 表达式解析（引依赖 + 边界多）——用**固定间隔**：`cron` 列存秒数（如 `3600`），
配置里 `[job] enabled = true/false` 总开关。理由写进注释：本项目内置任务都是「每小时/每天跑一次」，
间隔语义足够；要 cron 表达式是另一个量级。

**内置任务（代码注册，`admin/src/jobs.rs`）**
- `log_retention`：清理超过 `[log] retain_days` 的 login_log / audit_log（**复用阶段 1 A4 的实现**，
  从「启动时 spawn 一个固定 24h 循环」改造成「注册为 job」——保留 A4 的行为作为默认）
- `avatar_orphan_clean`：删除 `{upload_dir}/avatar/` 下不属于任何 admin 的文件（每天）

**接口**（权限码 `system:job:list/edit`）
```
GET  /api/v1/jobs?page&size&name&status        → Page<Job>
PUT  /api/v1/jobs/{id}                         { cron(秒), status }（名字与 code 不可改：代码注册）
POST /api/v1/jobs/{id}/run                     手动触发一次（同步执行并写 job_log）
GET  /api/v1/job-logs?page&size&job_code&status&start&end → Page<JobLog>
```

### C2b 通知公告

**目标**：管理员发公告，登录用户看到未读提示。
**数据模型**
```
notice(id pk auto, title varchar128, content TEXT, status i8（0草稿 1已发布）, created_by u64,
       published_at DATETIME NULL, created_at, updated_at)
notice_read(notice_id u64, admin_id u64, read_at DATETIME, PRIMARY KEY(notice_id, admin_id))
```
**接口**（权限码 `system:notice:list/add/edit/remove`）
```
GET    /api/v1/notices?page&size&title&status    → Page<Notice>（管理用）
POST/PUT/DELETE /api/v1/notices[/{id}]           增删改（发布 = status 置 1 并写 published_at）
GET    /api/v1/notices/unread                    当前用户未读列表（**登录即可**）
POST   /api/v1/notices/{id}/read                 标记已读（登录即可，写 notice_read）
```
**前端**：系统管理下新增「定时任务」「通知公告」两页；顶栏加一个铃铛（`Badge` 显示未读数，
点开是未读列表 + 标记已读）。

**验收**：任务手动触发写日志且能看到；调度循环真跑一次（用一个 2 秒间隔的测试任务，
或直接调用 job runner 的纯函数）；公告发布后未读接口返回、标记已读后从列表消失。

### C2 契约（先钉死，含糊处就是返工处）

**任务调度**
- `job.code` 是**代码注册键**：`admin/src/jobs.rs` 里一张 `&[JobSpec]` 表
  （`code` / `name` / 默认间隔秒 / 执行函数，函数签名 `async fn(&AppState) -> Result<String, String>`，
  返回的字符串进 `job_log.msg`）。表里没有的 code → 该行**不可手动触发**（409），
  避免库里残留的旧任务名被点到
- `job.cron` 存**间隔秒数**（字段名保留 `cron` 是为了将来换表达式时不改列名，注释写明）
- 调度循环：一个 tokio 任务，每 **10 秒** tick 一次，选出 `status=1` 且
  `last_run_at` 为空或已过 `now - 间隔` 的任务**串行**执行（不做并发：任务少，
  并发带来的写冲突不值得）。**同一进程内用 `last_run_at` 抢占**，避免 tick 重叠时重复跑
- `[job] enabled = true/false` 总开关（默认 true）；`false` 时**不启动循环**，
  但手动触发仍然可用（运维要能临时关掉定时、手动补跑）
- `POST /jobs/{id}/run` **同步执行**并把结果写 `job_log`，返回 `{ status, msg, duration_ms }`；
  执行超时不设（内置任务都是批删，见下）
- `log_retention` 沿用 A4 的实现，注册为 job（间隔 `[log] retain_days` 相同时的 86400），
  **A4 的启动时清一遍保留**（那不受 `[job] enabled` 影响——它是启动卫生，不是定时任务）
- `job_log` 也按 `[log] retain_days` 清理（并入 `log_retention`），否则执行记录无限涨
- `avatar_orphan_clean`：删 `{upload_dir}/avatar/` 下不属于任何 admin 的文件；
  **只删文件名是纯数字（admin id）的**，其他名字（用户手放的、临时文件）一律不碰（否则误删）

**公告**
- `status`：`0` 草稿 / `1` 已发布。**置 1 时写 `published_at`（仅当它还是 NULL）**；
  从 1 改回 0 不清空 `published_at`（留痕：曾发布过）
- `GET /notices/unread` → `{ total, list }`，`list` 为最近 **50** 条未读（已发布且当前用户
  在 `notice_read` 里没有记录的），按 `id DESC`；`total` 是未读总数（铃铛角标用它，
  不能拿 `list.length`——超过 50 条就少报了）
- `POST /notices/{id}/read`：**幂等**（`INSERT IGNORE` 语义），已读过再标记仍返回 200；
  目标是**草稿**时 404（草稿不属于任何人可见的未读集合）
- `DELETE /notices/{id}`：**同一事务里删 `notice_read`**（与字典的级联删一致），
  否则残留的行会让「已读」在新公告复用 id 时串味——本项目 id 自增不复用，但残留行仍是垃圾
- 只有**已发布**的公告进未读；草稿对普通用户完全不可见

**权限与菜单**
- 权限码：`system:job:list` / `system:job:edit`，`system:notice:list/add/edit/remove`
- `GET /notices/unread`、`POST /notices/{id}/read` **只认登录**（和字典下拉同理：
  这是每个登录用户都要有的能力，不该挂权限码）
- 菜单走 seed 幂等补齐，挂在系统管理下

**前端**
- 铃铛**只在本页挂载时拉一次 + 动作后刷新**，不做轮询（v1.6.0 明确不做；要实时是另一个量级）
- 未读弹层里点条目 → 调标记已读 → 从列表移除 + 角标减一；失败时不要乐观地把条目抹掉

## C3 完整 i18n（v1.7.0）

**范围（先定清楚，否则会变成无底洞）**
- **前端**：`zh-CN` / `en-US` 两套文案；antd 的 `ConfigProvider locale` 跟着切；语言存 localStorage + 跟随浏览器；
  切换入口放在顶栏（与主题开关并排）。
- **后端**：**不做 Accept-Language 的多语言消息** ✗ —— 改为**错误码 + 前端映射**：
  响应信封里 `code` 保持 HTTP 状态码（不改契约），额外返回一个稳定的业务错误码 `err`（如 `"auth.bad_credentials"`），
  前端按 `err` 查文案表，**取不到就回落到后端的中文 `msg`**（保证任何情况都有话可说）。
  理由：后端消息有 ~60 条，全部改造 + 维护两套是长期成本；而错误码是稳定契约，前端一张表就够。
  **只有现有消息需要加 `err` 的，才改后端**（一次性，约 60 处）。
- **不做**：数据库里的业务数据（菜单名、角色名、公告内容）多语言 ✗ —— 那是内容，不是界面文案。

**验收**：语言切换后界面文案与 antd 组件文案都变；后端返回的 `err` 能在前端表里命中；
未知 `err` 回落中文 `msg`；`pnpm test` 覆盖文案表与回落逻辑。

### C3 契约（前后端唯一的耦合点，先钉死）

**信封扩展**（向后兼容，原字段不动）：

```json
{ "code": 400, "msg": "备注长度不能超过 255 个字符",
  "err": "common.too_long", "args": { "field": "remark", "max": 255 }, "data": null }
```

- `err`：稳定的业务错误码，`模块.原因` 两段小写下划线（如 `auth.bad_credentials`）。
  **没有稳定码的消息就整个不带 `err`**（不是 `null`），前端回落 `msg`
- `args`：只有带参数的码才出现；**参数是给前端拼文案用的原始值**，不是已格式化的串
- `msg` 永远保留中文原文（日志、curl、没带文案表的客户端都还要用）

**模板消息也要可翻译**：`check_len` 这类通用校验现在拼的是中文字段名
（`"备注 长度不能超过 255 个字符"`）——前端没法翻译。改为**传字段键**：
`check_len("remark", v, 255)` → `err=common.too_long` + `args={field:"remark",max:255}`，
前端用 `field.remark` 查标签。**字段键查不到就原样显示键名**（宁可露出 `remark` 也别空着）。

```ts

export type I18nKey = keyof typeof zhCN;
// src/i18n/en-US.ts —— 写成 Record<I18nKey, string>，漏一个键就编译不过
export const enUS: Record<I18nKey, string> = { ... };
```

- `t(key, args?)`：`{name}` 占位替换；**键不存在时返回键名本身**（不抛异常，界面不至于白屏）

- 语言存 `localStorage`（键 `bee_admin_lang`），首次跟随 `navigator.language`；
  切换入口放顶栏（与主题开关并排）
- 切换时同步：`ConfigProvider locale`（antd 组件文案）、`dayjs.locale`（日期格式）、
  `<html lang>`
- **不做**：数据库里的业务数据（菜单名、角色名、公告内容）多语言——那是内容不是界面文案

## C4 继续压缩首屏体积（v1.8.0）

**现状**：首屏 1470 kB（antd 1251 + entry 127 + react 92）→ 已无「一个开关就下去 700 kB」的机会。
**先测量再动手**（不许拍脑袋优化）：
1. `pnpm build` 后对最重的 chunk 跑 `rollup-plugin-visualizer`（**dev 依赖**）出图，列出前 10 个模块及其体积。
2. 按测量结果选招，候选如下（按预期收益排序）：
   - **页面级懒加载是否真生效**：确认 7 个页面各自成块（现在 entry 127 kB 里可能混进了首屏不需要的东西）
   - **重组件按需**：`Table`/`Form`/`DatePicker` 等按需引入是否已生效（antd v5 是 tree-shake 的，若已被 tree-shake 则此项无收益）
   - **`dayjs` 的 locale 与插件**：只引 `zh-cn`/`en` 两种 locale + 用到的插件
   - **图标映射表**：C3 之后若图标名需要 i18n，别把整库再拖进首屏
3. **不做**换组件库 ✗（重写成本远超收益）。
4. 目标写进报告：**首屏 < 800 kB**（若测量表明达不到，就写实际达到的数字与原因，不硬凑）。

**验收**：改动前后 chunk 表对比 + 首屏总量数字 + 一次真实浏览器加载（CDP 记录传输字节）。

**落地结果（v1.8.0/v1.8.1）**：首屏 **1489.7 → 1103.6 kB**（拆 `manualChunks` 的 antd 数组写法，
把只有列表页用到的重组件移出首屏），再补上 **nginx gzip**（两个模板都没开，而 nginx 默认只压
`text/html`）→ **416.0 kB**，低于本项定的 800 kB 目标。
**教训**：第一次测量时用的静态服务本身没 gzip，把「服务没配压缩」误当成了「包太大」，
据此写下了「不换组件库就到不了」的错误结论（已在 v1.8.1 与 v1.8.0 的说明里更正）。
测首屏字节时，**被测环境的压缩配置本身就是口径的一部分**。

# 阶段 4b 契约 · 头像分片上传（aetherupload-rust 1.0.3）

> 本节是**前后端唯一耦合点**，两侧都照它实现；改协议先改这里。
> 已核实的插件事实（读源码，非 README 转述）：`Runtime::new(config, base_path)` 里
> `upload_root = base_path.join(config.root_dir)`，所以 **`root_dir` 传绝对路径 + `base_path` 传空串**
> 即可把上传根钉在 `[app] upload_dir`；分组名**不能含下划线**（含了就永久 404，插件在
> 唯一入口处直接拒）；`Config::default()` 自带一个 `file` 分组，我们要自己建 `avatar`。

## 为什么不直接挂插件的 `routes()`

插件那四条路由是**公开**的（`preprocess` / `uploading` 都在内）。头像接口现在**要求登录**，
直接挂等于开了一个无鉴权的写盘口 —— 加上文件名是 hash 派生的（每次上传都落**新文件**，
不像现在同名覆盖），那就是一条「任何人可无限写盘」的路径。

所以：**不挂插件的 Router，只复用它的内核**（`UploadController` + `FormData` + `PreprocessRequest`
+ `SaveChunkRequest` 都是 `pub`），自己写两个带 `Auth` 的薄 handler、自己的信封。
插件依赖只用核（`default-features = false`），**不开 `axum` feature** ——
顺带避开「插件 feature 拉 crates.io 的 bee_router 与本地 path 版冲突」那个老坑。

## 落盘命名：保持不了，所以改成记 `savedPath`

现在是 `{upload_dir}/avatar/{admin_id}.{ext}`；插件按
`{root_dir}/{group_dir}/{subdir}/{hash}.ext` 落盘，**文件名与目录都由插件定**。
于是：

- `admin.avatar` 列**改存插件的 `savedPath`**（不再是 URL）。对外 URL 仍由
  `avatar_url(id)` 生成 = `/api/v1/avatar/{hashids(id)}` —— **前端拿到的地址形状不变**，
  只有上传流程换。
- `GET /avatar/{id}`（公开，不变）内部：读该 admin 的 `avatar` 值 → 是 `savedPath` 就按
  上传根解析；是**旧值**（`/api/v1/avatar/xxx.png` 这种 URL）就回落到老的
  `{upload_dir}/avatar/{id}.{ext}`。**存量头像不用迁移就能继续显示。**
- `avatar_orphan_clean` 重写：头像组目录下的文件，凡不在任何 `admin.avatar` 里的一律删。

## 接口

两个都**要求登录**（`Auth`），multipart 表单，字段名与插件协议逐字一致。

### `POST /api/v1/avatar/upload/preprocess`

| 字段 | 必填 | 说明 |
|---|---|---|
| `resource_name` | 是 | 原文件名（插件据此取扩展名） |
| `resource_size` | 是 | 字节数 |
| `resource_hash` | 是 | 前端算的 md5（秒传/完整性用；不算就没有秒传） |
| `group` | 是 | 固定 `avatar` |
| `locale` | 否 | `zh` / `en` —— **插件的错误文案自己做 i18n**，前端按当前语言传 |

成功 `data`（插件原文透传）：

```json
{"error":0,"chunkSize":1048576,"groupSubDir":"202610","resourceTempBaseName":"…",
 "resourceExt":"png","savedPath":""}
```

- `savedPath` **非空 = 秒传命中**，一个分块都不用传，直接跳到「完成」。
- `chunkSize` 由服务端给，前端**必须用它**算分片（不要自己写死）。

### `POST /api/v1/avatar/upload/chunk`

| 字段 | 必填 | 说明 |
|---|---|---|
| `chunk_total` | 是 | 总分片数 |
| `chunk_index` | 是 | 第几片（**从 1 开始**） |
| `resource_temp_basename` | 是 | preprocess 返回的 |
| `resource_ext` | 是 | preprocess 返回的 |
| `group_subdir` | 是 | preprocess 返回的 |
| `resource_hash` | 是 | 同 preprocess |
| `group` | 是 | `avatar` |
| `resource_chunk` | 是 | **文件字段**，这一片的字节 |

成功 `data`：`{"error":0,"savedPath":""}`；**最后一片**返回的 `savedPath` 非空 =
组装完成。服务端在这一刻顺手：把 `admin.avatar` 写成该 `savedPath`、**删掉这位管理员
上一张头像文件**（否则每换一次头像就多留一个文件）。

### `GET /api/v1/avatar/{hashids_id}`（公开，**形状不变**）

### 错误

插件返回的 `error` 转成我们的信封：`400` + `msg` = 插件文案（**不带 `err` 码** ——
文案由插件的 `locale` 决定，不是我们表里的固定串）。前端按契约回落到显示 `msg`。

**删掉** `POST /api/v1/auth/avatar`（base64 那条）。两条上传路径 = 两套语义要维护，
且 base64 那条要先把整张图读进内存。前端同步改完，一次发布。

> **`chunk_size` 必须小于头像上限**：插件默认 1MB，而头像上限 512KB —— 用默认值的话
> **每个头像都恰好是一片**，「分片」在实际路径上永远不触发，除了秒传之外的功能全是摆设。
> 所以显式设 `chunk_size = 128 * 1024`：最大头像 4 片、典型压缩后的头像 1–2 片，
> 分片路径才真的被走到。**不加配置项**（这个值不需要按部署变）。
