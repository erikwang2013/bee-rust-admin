## C1 字典管理（v1.5.0）

**用途**：把「不改代码就能改的配置项」（性别、状态、业务枚举）搬进后台，前端下拉从这里取。

**数据模型（2 张表，走 syncdb）**

```
dict_type(id pk auto, name varchar64, code varchar64 UK, status i8, remark varchar255, created_at, updated_at)
dict_item(id pk auto, type_code varchar64 idx, label varchar64, value varchar64,
          sort i32, status i8, remark varchar255, created_at, updated_at,
          UNIQUE KEY uk_type_value(type_code, value))
```
- 字典项按 `type_code` 关联（不建外键，与现有风格一致）；`uk_type_value` 防同类型下 value 重复。
- 删除字典类型时**级联删除其字典项**（同一事务）；删除前若被引用？——本项目没有引用字典的地方，不校验。

**接口**（权限码 `system:dict:list/add/edit/remove`；菜单挂在系统管理下）

```
GET    /api/v1/dicts?page&size&name&status        → Page<DictType>
POST   /api/v1/dicts                              { name, code, status, remark }
PUT    /api/v1/dicts/{id}                         { name, status, remark }（code 不可改：它是关联键）
DELETE /api/v1/dicts/{id}                         级联删项
GET    /api/v1/dicts/{code}/items                 该类型全部启用项（**前端下拉用，登录即可访问**，不要求 system:dict:list）
GET    /api/v1/dict-items?page&size&type_code&label&status  → Page<DictItem>
POST   /api/v1/dict-items                         { type_code, label, value, sort, status, remark }
PUT    /api/v1/dict-items/{id} / DELETE /api/v1/dict-items/{id}
```
- `GET /dicts/{code}/items` 是**唯一对普通登录用户开放**的字典接口（下拉数据源）；其余都要权限码。
  返回 `[{label, value}]`，只含 `status=1`，按 `sort, id` 排序。
  **两种语义必须分开**（前端联调时发现原来混在一起）：类型不存在 → **404**（「字典类型不存在」，
  否则拼错 code 的人看到的是"空下拉"，分不清"没配数据"和"code 写错"）；类型存在但没有启用条目
  → **200 + `[]`**（合法状态，不是错误）。
- 导出：字典项列表也支持 `GET /dict-items/export`（复用现有 CSV 机制）。

**前端**：`system/dict/` 一页两栏（左类型列表、右该类型的字典项表格 + 增删改），路由 `/system/dict`，
守卫 `system:dict:list`；另加一个 `useDict(code)` hook（带内存缓存）供其他页面的下拉使用。

**验收**：字典类型/项的增删改查真库集成测试；级联删除；`{code}/items` 只返回启用项且普通用户可访问。

## C2 定时任务 + 通知公告（v1.6.0）

### C2a 定时任务

**目标**：后台里能看到「有哪些定时任务、上次跑成什么样、能不能手动跑一次」。**不做**在界面上写任意脚本
（那是 RCE 面）——任务用**代码注册**，数据库只管调度与执行记录。

**数据模型（2 张表）**

```
job(id pk auto, name varchar64, code varchar64 UK, cron varchar64, status i8,
    last_run_at DATETIME NULL, last_status i8 NULL, last_msg varchar255, created_at, updated_at)
job_log(id pk auto, job_code varchar64 idx, started_at DATETIME, duration_ms u64,
        status i8, msg varchar255, KEY idx_code_time(job_code, started_at))
```
**调度器**：不做 cron 表达式解析（引依赖 + 边界多）——用**固定间隔**：`cron` 列存秒数（如 `3600`），
配置里 `[job] enabled = true/false` 总开关。理由写进注释：本项目内置任务都是「每小时/每天跑一次」，
间隔语义足够；要 cron 表达式是另一个量级。

**内置任务（代码注册，`admin/src/jobs.rs`）**
- `log_retention`：清理超过 `[log] retain_days` 的 login_log / audit_log（**复用阶段 1 A4 的实现**，
  从「启动时 spawn 一个固定 24h 循环」改造成「注册为 job」——保留 A4 的行为作为默认）
- `avatar_orphan_clean`：删除 `{upload_dir}/avatar/` 下不属于任何 admin 的文件（每天）

**接口**（权限码 `system:job:list/edit`）
```
GET  /api/v1/jobs?page&size&name&status        → Page<Job>
PUT  /api/v1/jobs/{id}                         { cron(秒), status }（名字与 code 不可改：代码注册）
POST /api/v1/jobs/{id}/run                     手动触发一次（同步执行并写 job_log）
GET  /api/v1/job-logs?page&size&job_code&status&start&end → Page<JobLog>
```

### C2b 通知公告

**目标**：管理员发公告，登录用户看到未读提示。
**数据模型**
```
notice(id pk auto, title varchar128, content TEXT, status i8（0草稿 1已发布）, created_by u64,
       published_at DATETIME NULL, created_at, updated_at)
notice_read(notice_id u64, admin_id u64, read_at DATETIME, PRIMARY KEY(notice_id, admin_id))
```
**接口**（权限码 `system:notice:list/add/edit/remove`）
```
GET    /api/v1/notices?page&size&title&status    → Page<Notice>（管理用）
POST/PUT/DELETE /api/v1/notices[/{id}]           增删改（发布 = status 置 1 并写 published_at）
GET    /api/v1/notices/unread                    当前用户未读列表（**登录即可**）
POST   /api/v1/notices/{id}/read                 标记已读（登录即可，写 notice_read）
```
**前端**：系统管理下新增「定时任务」「通知公告」两页；顶栏加一个铃铛（`Badge` 显示未读数，
点开是未读列表 + 标记已读）。

**验收**：任务手动触发写日志且能看到；调度循环真跑一次（用一个 2 秒间隔的测试任务，
或直接调用 job runner 的纯函数）；公告发布后未读接口返回、标记已读后从列表消失。

## C3 完整 i18n（v1.7.0）

**范围（先定清楚，否则会变成无底洞）**
- **前端**：`zh-CN` / `en-US` 两套文案；antd 的 `ConfigProvider locale` 跟着切；语言存 localStorage + 跟随浏览器；
  切换入口放在顶栏（与主题开关并排）。
- **后端**：**不做 Accept-Language 的多语言消息** ✗ —— 改为**错误码 + 前端映射**：
  响应信封里 `code` 保持 HTTP 状态码（不改契约），额外返回一个稳定的业务错误码 `err`（如 `"auth.bad_credentials"`），
  前端按 `err` 查文案表，**取不到就回落到后端的中文 `msg`**（保证任何情况都有话可说）。
  理由：后端消息有 ~60 条，全部改造 + 维护两套是长期成本；而错误码是稳定契约，前端一张表就够。
  **只有现有消息需要加 `err` 的，才改后端**（一次性，约 60 处）。
- **不做**：数据库里的业务数据（菜单名、角色名、公告内容）多语言 ✗ —— 那是内容，不是界面文案。

**验收**：语言切换后界面文案与 antd 组件文案都变；后端返回的 `err` 能在前端表里命中；
未知 `err` 回落中文 `msg`；`pnpm test` 覆盖文案表与回落逻辑。

## C4 继续压缩首屏体积（v1.8.0）

**现状**：首屏 1470 kB（antd 1251 + entry 127 + react 92）→ 已无「一个开关就下去 700 kB」的机会。
**先测量再动手**（不许拍脑袋优化）：
1. `pnpm build` 后对最重的 chunk 跑 `rollup-plugin-visualizer`（**dev 依赖**）出图，列出前 10 个模块及其体积。
2. 按测量结果选招，候选如下（按预期收益排序）：
   - **页面级懒加载是否真生效**：确认 7 个页面各自成块（现在 entry 127 kB 里可能混进了首屏不需要的东西）
   - **重组件按需**：`Table`/`Form`/`DatePicker` 等按需引入是否已生效（antd v5 是 tree-shake 的，若已被 tree-shake 则此项无收益）
   - **`dayjs` 的 locale 与插件**：只引 `zh-cn`/`en` 两种 locale + 用到的插件
   - **图标映射表**：C3 之后若图标名需要 i18n，别把整库再拖进首屏
3. **不做**换组件库 ✗（重写成本远超收益）。
4. 目标写进报告：**首屏 < 800 kB**（若测量表明达不到，就写实际达到的数字与原因，不硬凑）。

**验收**：改动前后 chunk 表对比 + 首屏总量数字 + 一次真实浏览器加载（CDP 记录传输字节）。

## 通用规则（本组全部适用）

- 新模块一律沿用现有惯例：`#[derive(Model)]` + syncdb 建表、`ApiError` 统一信封、`auth.require(code)`、
  `datascope` 用于列表（若该模块有部门维度）、CSV 导出复用 `csv::response()`。
- 新增菜单与权限码**走 seed 的幂等补齐**（v1.2 已有），已部署的库重启即可拿到，不写手工迁移。
- 前端沿用现有结构：`api/<模块>.ts` + `pages/system/<模块>/index.tsx` + `RequirePerm` + `<Auth code>`。
- 每项完成后：真库集成测试 + `pnpm build` + 我本人复验 → 推送 → 发版。
