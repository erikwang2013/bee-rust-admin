### 2.2 产品决策：不做的理由（写下来就不用再吵一遍）

- **P1 sea-orm 式 DSL**：关联查询用 `relations.rs` 的 `get/set/del_relations` 三方法已覆盖现有需求；上游 `bee_orm` 也走这套。再上一层 DSL 是纯新增解析层，收益是「写法好看」，代价是长期维护一套查询语言。**没有具体查询写不出来之前不做。**
- **P2 多租户 / 部门之外的自定义数据权限**：`data_scope` 五档已覆盖现实里最常见的「按部门」需求。多租户要动全部 16 张表的主键与全链路过滤，是 v3 级重构，且当前没有任何租户场景需求。**真出现第一个多租户客户时再立项。**
- **P3 PUT 全量覆盖语义**：改成「缺省 = 不改」后，**「清空这个字段」就没法表达了**（除非再造一套显式 null 约定）。前端始终全量提交，收益只对直连 API 的对接方存在。改它是契约变更，不改只是文档里说明一句——现状已在 spec §9 和接口文档写明。**维持全量语义。**
- **P4 头像匿名读**：`<img src>` 带不了 Authorization 头，鉴权就得改签名 URL 或前端 blob 加载。头像属低敏信息，且收紧的代价（新机制 + 缓存失效 + 前端改造）大于收益。**接受现状。**（若哪天头像要放敏感物料，这条得重开。）
- **P5 登录锁定**：账号与 IP 共用阈值是**有意的安全取舍**——IP 桶若更宽松，攻击者能在自己额度内反复封受害者账号。内存态与 fail-open 也都有记录：限流是纵深防御，不是认证闸门。**维持。**唯一要盯的观测点：共享出口 IP 环境是否出现「一个人输错把整段 NAT 封掉」的投诉。
- **P9 审计空 body**：只在响应体已被消费、读取失败时触发，且已经打了 error 日志——**算不上静默，也算不上可达**。真要动也就一行；放进 patch 批次顺手做，不做也不欠什么。
- **`encryption-rust` 不接入**：已是用户拍板，理由完整记录在 `plans/2026-10-06-bra-v1.5-c-modules.md:542-571`（argon2id 强于 PBKDF2；唯一真空档是国密，属合规决策）。**本文不再列为待办。**

> **2026-10-11 补记**：D1 调研时发现的 3 处「注解与实现不符」**已经修掉**
> （`menu::remove` 的 404→400、`login_log::clear` 的返回类型、`admin` 列表 `dept_id` 的
> 「含子部门」）。同类的范围扫描结果：全仓库 12 个声称返回 404 的端点里只有 1 处是错的，
> 属零星漏网。所以 D1 现在**只剩 menu/dept 的请求体注解**要补。

### 2.3 全局速览：按「影响半径 × 代价」摆一次

| 格子 | 条目 | 处理方式 |
|---|---|---|
| 便宜 + 外人看得见 | D1（apidoc 空请求体）、D2（2/5 档测试）、D7（角色下拉） | **现在做**，不需要拍板（D7 的修法见 Q1） |

## 3. 发版分组建议

> **2026-10-12 补记（发布结果）**：下表 A–D 四组**已一次性发布为 v2.8.0**（见 §8）——
> 表里的 v2.6.3 / v2.7.0 / v2.7.1 三个版本号**不会再出现**，也**不欠三次发布**；
> 本节（含下面的「下一版应该装什么」）保留原样，只作追溯。

排序依据一句话：**先补「破了不会有人发现」的（D2），再清「对外可见且便宜」的（D1、D3–D5），
再验「用户第一步就会踩」的（D6），最后才是要等拍板的（D7、P6）。**

原则沿用既有节奏：一个批次一个版本、破坏性变更单列、patch 只装不改行为的修补。

| 组 | 版本建议 | 装什么 | 为什么放一起 | 风险 |
|---|---|---|---|---|
| A | **v2.6.3**（patch） | D2（数据权限 2/5 档集成用例）+ P9（若决定做，一行） | 都是**不改运行时行为**的加固：一个补测试、一个补兜底。patch 号符合 v2.6.1/2 的既有用法 | 低 |
| B | **v2.7.0**（minor） | D1（apidoc menu/dept 注解）+ D3/D4（spec §5.1/§5.3/§9 校准）+ D5（plan 复选框表态） | 一次把「文档与现实不符」清零。唯一改变**用户可见产物**的是 apidoc 站请求体不再空白，所以用 minor 而非 patch | 低（不碰运行代码） |

## 4. 需要负责人拍板的问题

每条给：这是什么 → 两条路的代价 → 推荐 → 不决定会怎样。

**Q1. 角色下拉的 100 条截断怎么修？**（D7）
- 路 A（小）：前端 `size` 改成 100 与后端一致，超过时在下拉里提示「仅显示前 100 条，请用搜索」——几行，消除「静默」这半个缺陷。
- 路 B（中）：改成远程搜索下拉（antd `showSearch` + `roleApi.list({ name })`），后端 `admin/src/api/role.rs:24-28` 已支持过滤，纯前端半天。
- **推荐 A**：角色数现实中基本不会破 100，B 是为不会发生的场景写代码。**触发条件**：真出现破 100 的部署再上 B。
- 不决定：截断继续静默，管理员会以为角色丢了，去查权限 bug。

**Q2. 数据权限 2/5 档是真在用的档位吗？**（D2）
- 这是先于测试的问题：**2（本部门及以下）和 5（自定义）现在有真实使用场景吗？** 在用 → 补测试（已列入 v2.6.3，成本小）。没人用 → 该决定的是**要不要从 UI 里撤掉这两档**，而不是给死代码补测试。
- **推荐**：按「在用」处理，先补测试（便宜、无风险）；撤档与否等有真实使用数据再说。
- 不决定：v2.6.3 就按「在用」走——这条不决定也不会错。

**Q3. 前端要不要引入 jsdom / RTL？**（P7）
- 路 A（引入）：+2 个依赖、CI 时长上升、得为渲染用例补一套写法；换来的是「权限按钮渲染、表单联动」这类回归有保护。
- 路 B（不引入）：继续手工回归——目前页面数稳定、手工走查做得勤，而最易碎的逻辑（权限判断、格式化）已经被 `.test.ts` 覆盖了。
- **推荐 B**，触发条件：出现**第一次纯逻辑测不到的渲染回归**，或页面数再明显增长。
- 不决定：默认维持现状（不引入），无损失。

**Q4. 头像接口要不要收紧？**（P4）
- 路 A（收紧）：签名 URL 或前端取 blob —— 新机制 + 缓存策略 + 前端改动，中成本。
- 路 B（接受）：`<img>` 直读、匿名可枚举 id。头像低敏，风险有限。
- **推荐 B**（与 spec §9 现有记录一致）。唯一的翻案条件：头像将来承载敏感物料。
- 不决定：维持匿名读，风险已知且已记录。

**Q5. 密码复杂度要不要加固？**（P6）
- 路 A（最小加固）：长度下限 6 → 8，且至少两类字符。改动点就两处硬编码（`admin/src/api/auth.rs:649`、`admin/src/api/admin.rs:104`）+ 前端提示 + 文档。
- 路 B（维持 6 位）：零成本，但这会写进对外文档，是一句公开的安全承诺。
- **推荐 A（最小版）**：成本小、只影响新设置/新改的密码（存量密码不受影响，登录不校验复杂度）。
- 不决定：维持 6 位——现状可用，只是这个档位偏低。

**Q6. 集成测试的共享库要不要拆？**（P8）
- 路 A（拆）：每个测试二进制用独立库名（改 fixture 里的库名常量），消除「并发跑两个 cargo 互相删表」。
- 路 B（维持）：CI 单流水线、cargo 串行跑各二进制，本机也是串行——除非你要**同时**跑两个 `cargo test`。
- **推荐 B**，触发条件：出现并行跑测试的真实需求（例如本机一边跑集成一边验证接口）。

## 5. 不在本路线图里的（运维动作，提醒但不排期）

这三件事是**部署时要做的动作**，不是代码任务，所以不进上面的分组：

1. **生产 `admin/conf/app.conf` 缺 5 个键**：`hashids_salt`、`hashids_min_len`、`snowflake_worker`、`snowflake_dc`，以及**必填**的 `encrypt_key`（缺了拒绝启动）。每次部署前对一遍 `.env.example`。
2. **上 v2.x 会让现有 token 全部失效**（JWT 的 iss/aud 是固定值，换版本即不认旧票）——升级窗口里所有在线会话要重新登录。
3. **v2.5.0 起前后端必须同版本换**：后端单独升、前端没跟上 → 头像上传 404（`POST /api/v1/auth/avatar` 已删除，改分片上传）。

三条都加进发布检查清单即可，不需要为它们写代码。
