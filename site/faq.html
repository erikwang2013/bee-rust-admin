5. 常见问题与运维

5.1 忘记超管密码了怎么办

超管密码只在首次启动（管理员表为空的那一次）按配置里的初始密码写入一次。之后改配置文件、重启服务都不会影响已经存在的账号，所以「改配置再重启」这条路是不通的；密码在库里也是加密哈希，翻不出原文。

界面上同样没有找回入口——系统有意禁止重置超级管理员的密码（「不能重置其他超级管理员的密码」），正是为了不让任何人借「重置」这条路接管超管。

实际可行的只有两种：

  • 你还登录着超管（比如浏览器没退）：直接去 个人中心 → 修改密码 改掉它。
  • 已经登不进去了：这属于运维动作，需要能碰服务器的人侧处理（按部署文档在数据库层面重置，或从备份恢复）。注意：清空管理员表能让系统在下次启动时重新写入初始超管，但所有管理员账号会一起丢失，不到万不得已不要这么做。

防患于未然：拿到初始密码后第一件事就是去个人中心改掉，并记进密码管理器。

5.2 账号被锁了，什么时候能再登

「尝试过于频繁，请 N 分钟后再试」是登录限流触发的，默认连续 5 次密码错误就锁 10 分钟。要点：

  • 触发维度有两个：同一个账号、同一个来源 IP（同一出口 IP 下的人可能互相「带累」）。
  • 验证码答错不计入失败次数，只有密码错才算。
  • 解锁方式就是等：窗口过去自动解除。成功登录会清掉该账号的失败计数；来源 IP 的计数要等窗口到期。
  • 计数保存在服务进程的内存里，所以服务重启会立刻清空。
  • 阈值本身是可配置项（失败次数、锁定时长），部署方可以按需要调；这两个值都设成 0（或负数）等于关闭限流。
  • 锁定的那一刻，如果配了 Webhook，会给接收端推一条 account.locked（哪个账号、来源 IP、解锁时间，见 3.13）。

5.3 语言和主题在哪里改，为什么换了台电脑就变了

都在顶栏：切换语言、切换明暗主题。它们只保存在你这台电脑的浏览器里，不跟账号走——换设备、换浏览器、清浏览器数据之后都会回到默认（语言跟随浏览器、主题跟随系统）。

5.4 头像传不上去

按提示对症处理：

现象 / 提示 原因与处理
图片读取失败，请换一张 PNG/JPEG 选的文件不是 PNG/JPEG（改了后缀的也不行），换一张真图
压缩后仍超过 512KB，请换一张小一些的图片 浏览器自动压缩后仍然超过 512 KB，换一张尺寸更小的图
头像不能超过 512 KB 服务端硬上限拦截，同上，换小图
头像上传失败 网络中断或服务不可用，重试一次；持续失败找管理员看服务状态

别忘了上传过程中有进度显示，大图（接近 512 KB）在慢网络下要等几秒，别急着关页面。

5.5 公告发布了，为什么有人看不到

按顺序检查：

  1. 它还是草稿吗？列表里状态为「草稿」的公告对普通用户完全不可见，必须在列表里点 发布。
  2. 对方看错地方了吗？未读提示在顶栏铃铛里，不在侧边栏菜单里。
  3. 是不是已经被 取消发布 了？取消发布后它会从所有人的未读里消失（已读记录还留着，重新发布不会重复提醒已经读过的人）。
  4. 铃铛里一次只列最近 50 条未读，如果对方积压了很多条，旧的那条可能没显示出来，列表底部会提示「还有 n 条未读」。

5.6 定时任务为什么没跑

依次排查：

  1. 调度开关：部署配置里 [job] enabled 为 true 时，服务才会启动调度循环。它被关掉时，自动调度完全停摆，但手动 触发一次 仍然可用——先用「触发一次」确认任务本身没问题。
  2. 任务状态：列表里显示 停用 的任务不会被调度（但上面说了，仍然可以手动触发）。
  3. 间隔没到：任务按「上次运行时间 + 间隔」判定，间隔单位是秒；列表里的「间隔（秒）」和「上次运行」可以直接对。
  4. 从来没跑过：新装或新加的任务「上次运行」显示 从未运行，服务起来后第一个检查周期（10 秒内）就会补跑一次；如果一直没跑，回到第 1、2 条。
  5. 跑了但失败：「执行记录」页签里看每次执行的 结果 和 消息（列表的「上次结果」也写着最后一条结果）。任务失败不会重试，等下一个间隔再跑。

5.7 升级后为什么要重新登录

登录令牌里带了一个版本号。服务端每次请求都会拿它和账号上的版本号比对，对不上就判定为失效——界面表现是跳回登录页，提示「登录已失效，请重新登录」。

会让版本号变动、从而让所有已签发的旧令牌立即作废的操作有：

  • 退出登录、退出其他设备；
  • 修改密码、被管理员重置密码；
  • 账号被禁用。

所以「升级后要重新登录」通常不是升级这个动作本身造成的，而是上面某件事（或者升级时顺手换掉了签名密钥）的结果。重新登录一次即可，数据不受影响。反过来看，这也是为什么重置别人密码之后要记得通知他：他会被立刻踢下线。

5.8 操作日志里的「安全扫描命中」是什么

那是请求安全扫描的记录：服务会对每个请求做一遍攻击特征检测（SQL 注入、命令注入、路径穿越、SSRF 之类），命中的请求会在 操作日志 里留下一行，模块是 security、动作是 安全扫描命中。

关键点：

  • 默认只记录、不拦截：默认配置下命中的请求照常执行，只是留一条痕。这是有意的——误报真实存在（密码里带 ' or 1=1-- 的用户名、公告里贴的代码片段），直接拦会误伤正常工作。
  • 部署方可以把扫描调成「命中高危就拦截」；那种情况下被拦的请求会直接返回失败（提示 请求被安全策略拦截），日志里那行的结果会是失败——这时候用户在界面上看到的是操作没成功，而不是「服务坏了」。
  • 日志里只记等级和检测器的名字，不记请求的原始内容，所以别指望从这行里翻出对方到底发了什么；真要追查，结合同一时间的其它日志一起看。

5.9 运维 · 清理明文备份

这一条给能碰数据库的运维看，普通使用者可以跳过。

表 admin_email_phone_backup 是 email / 手机号存量加密迁移留下的明文备份：迁移把库里原有的明文字段逐行加密回写，写之前先把原值存进这张表 —— 密钥一旦丢了或换错，密文就解不开了，这是唯一的退路。反过来说，只要它还留着，明文 PII 就一直敞在库里，确认不需要了就该清掉。

清理前必须验证：当前密钥能正常解密。登录后打开 个人中心，邮箱、手机号要显示原文（能正常读写即解密正常）。看不到原文就不算验证过 —— 页面能打开、显示空白或脱敏值都不能证明密文解得开。

还要看一眼启动日志里有没有「加密失败，暂留明文」：服务每次启动都会把存量明文逐行加密，个别行搬不动（比如密文撑爆列宽）就留在原处、日志点名、下次启动再试。出现过这一行就说明库里还有明文行 —— 那行没搬完之前先别清：清了备份表，下次启动又会把它重新写进（新建的）备份表。

验证通过、且升级后确定不需要回滚了，就可以清理（不可逆，清完没有任何回退手段，密钥再丢就真的找不回了）：

DROP TABLE admin_email_phone_backup;

建议清之前先把表导出一份留档，存进密码管理器或离线位置：

mysqldump bee_admin admin_email_phone_backup > admin_email_phone_backup.sql

服务每次启动都会数一下这张表的行数，还有数据就在日志里 warn 一行提醒；清掉之后提示自然消失。

清完表又冒出来（空表）是正常的：启动迁移里有 CREATE TABLE IF NOT EXISTS，删掉的表会在下次启动时以空表重建 —— 空 = 清理成功，别当成没清掉；只要行数是 0，就没有明文留在库里。

5.10 运维 · 数据库备份与恢复

这一条也是给运维看的。内置任务 数据库备份（db_backup）把整个库用 mysqldump 导到磁盘上，默认每天跑一次。要点：

  • 落在哪：[backup] dir 指定的目录；不配就落在 {upload_dir}/backups/（默认即 uploads/backups/）。文件名形如 backup_20261016_030000.sql，权限 0600（dump 里是全库数据，包括口令哈希，别改成同机可读）。
  • 留几份：[backup] keep，默认 7 份；每跑完一次就删掉多余的最旧备份。keep 必须是 ≥ 1 的整数，配成 0 或负数服务会拒绝启动（等于每跑一次就把备份全删了）。
  • 怎么立刻备一份：定时任务页里对 数据库备份 点 触发一次（立即受理、后台执行，不占着页面等），到 执行记录 页签里看这次跑的耗时与消息（含文件名和字节数）。
  • 任务失败不算接口失败：跟其它任务一样，结果看执行记录里的 status 与 msg（常见原因：mysqldump 没装、DNS 里的账号密码不对、磁盘满）。
  • 恢复是手工动作（不做自动恢复，避免误触发覆盖现网）：先在库里确认要恢复的 dump 文件，然后

bash # 1) 停服务（别带业务写入做恢复） sudo systemctl stop bee-admin # 2) 恢复（口令走环境变量，别进命令行历史） MYSQL_PWD='口令' mysql -h 127.0.0.1 -u 用户 bee_admin < /path/to/backup_20261016_030000.sql # 3) 起服务 sudo systemctl start bee-admin

恢复会按 dump 里的 DROP TABLE IF EXISTS + CREATE TABLE 覆盖同名表，库里 dump 之后的新数据会没掉——这就是要先停服、想清楚的原因。恢复完照常登录（账号数据也来自 dump，用当时的密码）。 - mysqldump 用的连接参数就是从 [db] dsn 里拆出来的（同一份凭据），所以备份能不能跑通可以直接用 mysql 客户端拿同一组参数试。

5.11 通知没发出去 / 测试邮件失败

  • Webhook 没收到：先看开关和地址（必须是 http:// / https:// 开头，保存时就会拦；地址写 IP 字面量 时（按 URL 规范化后的 host 判定），169.254.0.0/16、fe80::/10、0.0.0.0、:: 这类链路本地 / 未指定地址也会被拒，127.0.0.1 等回环允许）。发送时还会解析域名：解析结果只要有一个落在链路本地 / 未指定地址，就不投递、记终态失败（notify_delivery.status = failed，msg 里写「链路本地」），域名解析到链路本地 / 未指定地址会被拦、也不会重投；保存时放行的域名不等于发送时一定放行（RFC1918 私网 / IPv6 ULA 不拦，需部署侧网络策略兜底）。再看接收端要求 —— 我们发的是 POST + Content-Type: application/json，body 是 {"event","at","data"}；配了签名密钥还会带 X-BRA-Timestamp / X-BRA-Signature（HMAC-SHA256，算法见 3.13）。接收端回非 2xx（含 3xx —— 我们不跟随重定向，不会把请求带到 Location 去）、5 秒没响应或连接失败，都算一次失败：落 notify_delivery 账本，首发失败 1 分钟后由 notify_retry 重投，之后按 5/15 分钟退避，最多重投 3 次（共 4 次尝试）后置 failed；成功置 delivered。排查看 notify_delivery 的 msg 与任务执行记录里的 notify_retry（账本保留 30 天）。
  • 失败的事件会重投，但不保证顺序：Webhook 首发失败才落 notify_delivery 账本（成功不落行），由 notify_retry 重投，所以「对方服务器重启那 2 分钟里失败的事件」会在恢复后按退避收到。接收端请按 event + at（或 body 里的业务键）做幂等去重 —— 重投可能乱序，也可能重复。发送时域名解析命中链路本地 / 未指定地址是终态失败、不重投；账本保留 30 天，过期后不再补。公告的邮件推送仍不落库、失败不重投（它只负责提醒去看公告）。
  • 测试邮件失败：提示里就是原因。常见的几条：connection refused / 超时（主机名或端口不对，或对方只在内网通）、authentication failed（用户名 / 口令不对，或者服务商要求用应用专用密码）、证书相关报错（加密方式选错了：465 用 SSL/TLS、587 用 STARTTLS）、sender address rejected（发件人不是服务商允许的地址 —— 多要求发件人 = 认证账号）。测通了记得把 SMTP 开关打开，测试邮件本身不看开关。
  • 收件箱里没有：先翻垃圾邮件 / 已过滤；再把发件人换成服务商允许的地址重试一次。
