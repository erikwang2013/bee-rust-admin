# BRA Installation Guide

Bee Rust Admin — Rust backend `bee_admin` + React frontend dist + MySQL 8 + nginx.
This guide is for operators: how to install it. For day-to-day use see the [User Guide](usage.html); for troubleshooting and operations see the [FAQ](faq.html).

---

## 0. Prerequisites

| Item | Requirement | Notes |
|---|---|---|
| OS | **Linux x86_64** | ARM requires a source build or Docker (no arm64 prebuilt binary) |
| Database | **MySQL 8.0+**, charset `utf8mb4` | Tables and the superadmin account are created automatically on first start; no manual SQL import |
| glibc | **≥ 2.38** | Only required for prebuilt binaries, see below |
| Privileges | root or sudo | Needed only for the systemd unit / nginx site step; everything else can run as a normal user |

### ⚠️ The most important one: glibc

The prebuilt binary requires **glibc ≥ 2.38** (Debian 13 / Ubuntu 24.04 or newer).
On Ubuntu 22.04 (2.35), Debian 12 (2.36) or CentOS it fails with
`version 'GLIBC_2.38' not found`; the binary simply cannot start.

```bash
ldd --version | head -1     # the last number is your glibc version
```

**If it is below 2.38, take a different path**: use a source build (`--mode build`) or Docker.

> `install.sh` checks this itself — it makes the downloaded binary **actually load once**.
> If it cannot run, the script exits **before writing anything** and prints the two alternatives,
> so you never get a half-installed service that cannot start.

## 1. Generate configuration

Three secrets in `app.conf` must be generated by you (**do not use the example placeholders; the service refuses to start**):

```bash
# Database password (plain text is fine; the script/examples handle it)
# Encryption key for encrypted columns (AES-256-GCM) — must be 32 bytes
echo "encrypt_key = base64:$(openssl rand -base64 32)"
# Salt for public short ids
echo "hashids_salt = $(openssl rand -hex 16)"
# JWT signing secret (≥32 characters)
echo "secret = $(openssl rand -hex 32)"
```

Then fill this into `<prefix>/conf/app.conf` (mode `600`):

```ini
[app]
name = bee-rust-admin
http_addr = 127.0.0.1:8080
log_level = info
upload_dir = uploads
hashids_salt = <hex generated above>
hashids_min_len = 8
snowflake_worker = 0
snowflake_dc = 0
encrypt_key = base64:<value generated above>

[db]
dsn = mysql://<user>:<password>@127.0.0.1:3306/bee_admin

[jwt]
secret = <hex generated above>
expire_hours = 24

[auth]
max_fail = 5
lock_minutes = 10
captcha = true
captcha_trajectory = false

[log]
retain_days = 90

[job]
enabled = true

[security]
scan = off

[apidoc]
enabled = false
password =

[seed]
initial_admin_password = <choose one>
```

> ⚠️ **`encrypt_key` and `hashids_salt` cannot be changed after generation**:
> changing `encrypt_key` means encrypted email/phone columns can **never be decrypted again** (no recovery);
> changing `hashids_salt` invalidates every public short id already issued. **Back up this conf once generated.**

> ⚠️ `initial_admin_password` is used only on the **first start (when the admin table is empty)** to create the built-in `admin` user.
> If it is too weak (shorter than 8 characters, or fewer than two of letters/numbers/symbols) the **first** start is rejected with a clear error;
> once the database is non-empty this key has no effect. Validation is deliberately **not** done while loading config —
> so an existing deployment with an old password in the conf can still start until you change it.

See [`admin/conf/app.conf.example`](../admin/conf/app.conf.example) for every key, defaults and notes such as “must differ per instance”.

## 2. Three ways to install

### (a) One-command script (recommended)

**Clone the repository first; do not pipe `curl | bash`** — the script needs root for systemd and nginx, so read it first.
`install.sh` is only the entry point; the steps live in `scripts/lib/install-*.sh` in the same repo (missing files cause an immediate error).
The old “download a single `install.sh` and pipe it” flow is retired — clone the full repository:

```bash
git clone --depth 1 https://github.com/erikwang2013/bee-rust-admin.git
cd bee-rust-admin
less install.sh          # inspect first (steps live in scripts/lib/install-*.sh)
bash install.sh          # interactive: asks for the database password
```

It then: downloads the release artifacts (binary + frontend dist) → generates secrets → writes `<prefix>/conf/app.conf` (0600)
→ optionally creates the database → installs the systemd unit + nginx site → starts the service and checks `/api/v1/health`.
The default prefix is `/opt/bee-admin`, exposed on `8081`.

- **Database creation is optional**: pass `--db-admin-user U --db-admin-pass P` to create the database and user automatically;
  otherwise it prints SQL for you to run (it does not guess the root password, does not `DROP`, and does not install MySQL).
  **Upgrades (`--keep-conf`) never create a database or user**: connection credentials come from the existing `app.conf` dsn; `--db-*` is ignored;
  if the connection fails it exits and lets you fix the dsn (it never alters an existing database account).
- Tables and the superadmin are created automatically on **first start**; no manual SQL import.

Common variants (see `install.sh --help`):

```bash
# Older machines (glibc < 2.38): build from source (needs rust 1.99+ / node 22.12+ / pnpm 10+)
bash install.sh --mode build

# Install a second instance (separate directory, service name, ports and snowflake node)
bash install.sh --service-name bee-admin-2 --prefix /opt/bee-admin-2 \
                --http-port 8091 --backend-port 8090 --snowflake 2,0

# See what it would do (no writes, downloads or DB connections)
bash install.sh --dry-run --yes

# Upgrade: replace only the binary and service files; configuration is untouched (--db-* ignored, DSN from existing conf)
bash install.sh --keep-conf ...

# No root / manage the process yourself: skip systemd (and service restarts; manual start command is printed);
# add --no-nginx to skip the nginx site too
bash install.sh --no-systemd --no-nginx
```

> **If `app.conf` already exists the script refuses to overwrite it by default** (exit code `6`) — changing `encrypt_key`
> makes encrypted email/phone columns permanently unreadable. To overwrite, pass `--force`: it backs up the old file to
> `app.conf.bak.<timestamp>`, but data may still be undecryptable after a key change — only use it when you understand the consequence.
> **Use `--keep-conf` for normal upgrades.**

**Exit codes**: `0` success · `1` argument/build failure · `2` preflight failure (nothing written) · `3` ready except root commands ·
`4` database needs manual creation · `5` self-check failed · `6` existing configuration found without `--force`.

### (b) Docker Compose

The repository includes `docker-compose.yml` (MySQL + backend + frontend, exposed on `8081`) and the helper
`compose-up.sh` (generates missing passwords/secrets and writes them to `.env` and `admin/conf/app.conf`):

```bash
./compose-up.sh --build     # generates missing passwords/secrets and starts the stack; drop --build when images exist
# Open http://localhost:8081 (account admin; initial password is in secrets/initial_admin_password)
```

- The container database address is injected via `BEE_ADMIN_DB_DSN` (pointing at the compose `mysql` service);
  the config file is mounted from the host `admin/conf/app.conf`, and JWT secret / initial password are read from it.
- Uploads, exports, attachments and database backups live in the host `data/bra/` directory (mounted at `/home/uploads`),
  not in the container layer; MySQL data is in the `mysql-data` volume. Logs use rotated json-file, `/tmp` and nginx caches use tmpfs.
- Abandoned `_header/` / `.part` upload files and `backup_*.sql.part` older than 24 hours are reclaimed by the built-in cleanup jobs;
  nginx streams `/api/` requests and responses instead of buffering them into the 32MB tmpfs.
- The backend container runs as **the owner of the host config file** (`APP_UID`/`APP_GID` in `.env`; a fresh `.env` uses the current user, existing explicit values are kept):
  `app.conf` is usually mode 600, so the image’s default non-root user cannot read it and the service fails to start.
  Change `APP_UID`/`APP_GID` explicitly if your host uid/gid differs (`id -u` / `id -g`); root only chowns app.conf/data when the owner differs.
- Uploaded avatars go to `/home/uploads` (the `data/bra/` bind mount), so they survive container recreation.
- `compose-up.sh` only fills empty/placeholder values (existing values are left alone; rerunning does not regenerate them);
  local secrets live in `secrets/` (0600). Back up `secrets/` and `admin/conf/app.conf` (losing `encrypt_key` makes encrypted
  email/phone permanently unreadable). Old `.env` / app.conf DSN passwords are migrated, including external MySQL passwords;
  a legacy TLS `HTTP_PORT=80` is reset to 8081 by `--http`.
- To use an existing MySQL: remove the compose `mysql` service and `depends_on`, then change `BEE_ADMIN_DB_DSN`.
- **Do not want to build locally** (no Rust/Node toolchain): every Release also ships `bra-images-vX.Y.Z.tar.gz`
  and `bra-compose-vX.Y.Z.tar.gz` offline packages (images are built on the maintainer’s machine; `docker load -i` imports them;
  the compose package contains the compose file, `compose-up.sh`, a prefilled `.env` and a one-page README) — unpack,
  `docker load -i`, then run `./compose-up.sh` (without `--build`). See the Docker section in the root README.

### (c) Manual deployment

systemd runs the backend (listening on `127.0.0.1:8080`); nginx exposes `8081`:

```bash
cargo build --release -p bee_admin
cd admin/web && pnpm build

sudo cp admin/deploy/bee-admin.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now bee-admin

# The nginx site directory depends on your nginx: source builds often use <prefix>/conf/vhost/, distros use /etc/nginx/conf.d/
sudo cp admin/deploy/nginx.conf.example /usr/local/nginx/conf/vhost/bee-admin.conf
sudo nginx -t && sudo systemctl reload nginx
```

> The paths and username in those two files are **examples** (`/home/wwwroot/bee-rust-admin` and `erik`); change them to your own values —
> or use `install.sh`, which renders the files from the actual paths / user / ports.

**Machines without root / sudo can use a user-level unit**, with the same capabilities:

| | System-level | User-level (no root) |
|---|---|---|
| Unit file | `admin/deploy/bee-admin.service` | `admin/deploy/bee-admin.user.service` |
| Install | `sudo cp` to `/etc/systemd/system/` | `cp` to `~/.config/systemd/user/`, no sudo |
| Start at boot | supported directly | one-time `sudo loginctl enable-linger <user>` (`loginctl show-user <user> -p Linger`; otherwise it starts only after that user logs in) |
| Manage / logs | `systemctl status/restart bee-admin`, `journalctl -u bee-admin` | same commands with `--user` (root’s `systemctl status` cannot see user units) |
| Restart on crash | `Restart=on-failure`, retry after 3 seconds | same |

```bash
# User-level install (no root; paths are examples from a local setup)
mkdir -p ~/.config/systemd/user
cp admin/deploy/bee-admin.user.service ~/.config/systemd/user/bee-admin.service
systemctl --user daemon-reload && systemctl --user enable --now bee-admin
```

Daily operations (upgrade = rebuild the binary, then restart):

```bash
systemctl --user status bee-admin          # drop --user for system-level
systemctl --user restart bee-admin
journalctl --user -u bee-admin -f          # follow logs
```

> ⚠️ The two unit templates use different `WorkingDirectory` values (system-level `<repo>/admin`, user-level **repo root**) —
> `uploads` is resolved **relative to WorkingDirectory**. When migrating an existing deployment, keep the original cwd, or avatars will 404.

## 3. Post-install checks

```bash
curl http://127.0.0.1:8080/api/v1/health     # => OK
```

Then open `http://<machine address>:8081` (replace the port if you changed it),
log in with `admin` + `[seed] initial_admin_password`, and **change the password immediately**.

## 4. Common pitfalls

- **`app.conf` is mode 600**: the service user must own it, or the service cannot start; in containers match `APP_UID`/`APP_GID`.
- **`encrypt_key` cannot be changed**: changing it makes encrypted email/phone permanently unreadable (no recovery). Back it up with the whole `app.conf`.
- **Changing `hashids_salt`** invalidates every public short id already issued.
- **The initial password only applies when the database is empty**: if `admin` already exists, it is ignored; change the password in the UI.
- **Upgrade the backend and frontend together**: the new backend removed the old base64 avatar endpoint; an old frontend against a new backend gets a 404 on avatar upload.
- **Captcha is on by default** (`[auth] captcha = true`): login takes one extra step; wrong captcha answers do not count toward lockout.
- **Drag-trajectory validation is off by default** (`[auth] captcha_trajectory`): when enabled, slider answers must include a trajectory
  (plugin defaults: ≥4 points, 300–5000 ms, linearity ≤0.99); clients that send only the raw value fail.
  The new frontend always reports trajectories, so enabling it does not require a frontend redeploy; the cost is that an extremely fast flick (<300 ms) is treated as a bot —
  users see “captcha error” no matter how they drag; adjust the plugin’s `min_duration_ms` to relax it.
- **`install.sql` in the repository root is unrelated** (it is another tool’s schema); installation does not need it.
- **Forgot the superadmin password**: update the `admin` table in the database (or recreate the database).
